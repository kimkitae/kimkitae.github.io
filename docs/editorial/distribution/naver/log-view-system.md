# 자동화 도구가 늘어날 때 로그를 한곳에서 보는 방법

자동화 도구가 여러 개로 늘어나면 “지금 어디서 실패했는지” 확인하는 일이 병목이 됩니다. New Relic, Datadog, Grafana 같은 도구가 이미 있지만, 간단한 로그 한 줄을 보려고 전체 관측 시스템을 붙이는 것은 과할 때가 있습니다. 작은 LogViewer를 만들면서 배운 핵심은 컴포넌트 목록이 아니라 **저장과 실시간 전달이 서로 다른 실패를 가진다**는 점입니다.

## 두 경로를 나눠서 본다

API 서버가 로그를 Kafka `log` 토픽으로 보내고, 컨슈머가 MariaDB에 저장한 뒤 Redis `log` 채널에 발행합니다. 웹 UI는 WebSocket으로 실시간 로그를 받습니다.

- **저장 경로**: API → Kafka → 컨슈머 → MariaDB. 나중에 조회할 이력을 만듭니다.
- **실시간 경로**: 컨슈머 → Redis Pub/Sub → WebSocket → 브라우저. 지금 화면을 갱신합니다.

[Redis Pub/Sub 문서](https://redis.io/docs/latest/develop/pubsub/)는 Pub/Sub이 메시지를 저장하지 않으며, 구독하지 않은 동안의 메시지를 나중에 받을 수 없다고 설명합니다. 즉 실시간 경로는 놓친 전달을 재생하지 않습니다. 놓친 로그는 DB에서 읽어야 합니다.

원문 컨슈머는 DB 저장 후 Redis에 발행합니다. DB 저장이 실패하면 발행도 실행되지 않아 이력과 화면 모두에 로그가 없습니다. 반대로 발행이 실패하면 DB에는 남지만 화면에는 보이지 않습니다. 같은 “로그가 안 보인다”는 증상이 정반대 원인을 가질 수 있습니다.

## 일시정지는 수집을 멈추지 않는다

원문 UI는 `isPaused`가 참이면 화면 표시만 건너뜁니다. 서버 수집과 DB 저장은 계속됩니다. 그리고 일시정지를 해제하거나 태그 필터를 바꾸면 `fetchLogsForService`가 DB에서 로그를 다시 가져옵니다(원문 웹 UI 코드, `source` 328-368행). 원문 주석은 “새로고침 할 경우에만 DB에서 가져온다”고 적지만 실제 코드는 재개와 필터 변경에서도 조회합니다.

이 차이가 진단에 유용합니다. 일시정지 후 재개했을 때 로그가 채워지면 저장 경로는 살아 있고 실시간 경로만 끊겼을 수 있습니다. 재개해도 그 구간이 비어 있으면 저장 경로를 의심합니다.

## 실패 지점별로 확인할 것

| 실패 지점 | 증상 | 확인할 증거 | 다음 조치 |
|---|---|---|---|
| API → Kafka 전송 | 실패해도 API가 성공으로 응답할 수 있음 | 프로듀서 예외 로그, 실제 토픽 수신 | 응답과 실제 전달 결과 대조, 실패를 호출부에 전달 |
| 컨슈머 DB 저장 | 실시간에도 이력에도 없음 | 컨슈머 예외 로그, DB 행 수 | 알림과 재처리 가능 여부 확인 |
| Redis 발행 | DB에는 있는데 화면에 없음 | DB 조회 결과와 화면 비교 | 새로고침·필터 조회 확인 |
| 클라이언트 끊김 | 끊긴 동안 화면에 없음 | WebSocket 종료 코드, 재연결 로그 | 재연결 후 DB 재조회 여부 확인 |
| 중복 수신 | 같은 로그가 두 줄 | 메시지 키, DB 중복 행 | 멱등 처리와 유니크 키 |

원문 프로듀서는 전송 예외를 로그에 남기고 호출부에 다시 던지지 않습니다. 그래서 API가 성공으로 응답해도 실제 토픽 수신 여부를 대조해야 합니다. 컨슈머 예시에는 루프 안의 예외 처리가 없고, 태스크 재시작 설정도 나오지 않습니다. DB 오류 뒤 소비가 계속되는지 별도로 확인해야 하는 이유입니다.

“DB에는 있는데 화면에 없다”면 해당 로그의 실시간 경로부터 확인합니다. 원문은 메시지 키를 `{service_name}_{timestamp}`로 만들지만 컨슈머 재처리 시 중복 저장을 막는 장치는 나오지 않습니다. exactly-once를 보장한다고 주장하면 안 됩니다.

## 지금 다시 만든다면

FastAPI의 `@app.on_event("startup")` 대신 `lifespan` 컨텍스트를 쓰는 편이 좋습니다. 연결과 정리를 한곳에 모을 수 있고 테스트하기도 쉽습니다.

로그량이 크지 않고 소비자가 하나라면 Kafka는 운영 비용이 더 큽니다. 브로커, 토픽, 파티션, 컨슈머 그룹을 관리해야 하고 장애 시 처리 지점을 확인하는 일도 늘어납니다. 서버에서 클라이언트로만 보내면 되는 경우 SSE가 WebSocket보다 단순하고, 클라이언트가 서버로 업무 이벤트를 보내야 할 때 WebSocket을 검토합니다. 재생이 필요하면 Redis Pub/Sub 대신 Redis Streams나 DB 폴링을 검토합니다. 이것은 현재의 설계 판단이며 원문 시스템을 실제로 이 구조로 바꿨다는 기록은 아닙니다.

## 운영에서 먼저 정할 것

인증번호, 토큰, 주문 상세처럼 민감한 값은 클라이언트 단계에서 마스킹해야 합니다. 서비스별 보관 기간도 정해야 합니다. UI는 서비스 선택, 태그·레벨 필터, 일시정지, 페이지네이션, 연결 상태 정도로 단순하게 유지하고, “로그가 안 보일 때 원인을 알 수 있는가”를 기준으로 삼으세요.
