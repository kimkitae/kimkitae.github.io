# 알림음 자동 검증, “매칭됐다”가 증명하는 것과 하지 않는 것

알림음은 화면에 흔적을 남기지 않습니다. 그래서 오디오 지문으로 매칭 결과 하나를 얻으면 검증이 끝났다고 느끼기 쉽습니다. 하지만 그 결과는 네 질문 중 하나만 답합니다. 녹음에 소리가 들어 있었는지, 소리가 실제로 발생했는지, 그 소리가 기대한 알림음인지, 사용자가 알림을 받았는지입니다.

먼저 바로잡을 점이 있습니다. 예전 글에서 Docker Hub의 `appbaseio/dejavu`를 오디오 지문 도구로 소개했는데, 그것은 Elasticsearch 데이터 뷰어입니다. 오디오 지문에는 [`worldveil/dejavu`](https://github.com/worldveil/dejavu)를 써야 합니다. 원문 환경은 Docker Compose로 PostgreSQL을 실행하고 `songs`, `fingerprints` 테이블을 사용했습니다.

## 1. 녹음에 오디오가 있는가

Android의 `adb shell screenrecord`는 영상만 기록하고 오디오를 포함하지 않습니다([공식 문서](https://developer.android.com/tools/adb#screenrecord)). Appium의 Android 화면 녹화도 같은 명령을 쓰는 경우가 많으므로 파일을 직접 확인해야 합니다. 원문은 단말의 Screen Recording을 사용했다고만 적었고, 그 파일에 오디오가 있었는지는 확인할 수 없습니다.

```bash
ffprobe -v error -select_streams a:0 -show_entries stream=codec_name -of csv=p=0 notification.mp4
```

출력이 비어 있으면 오디오 스트림이 없습니다. 이것은 “알림음이 나지 않았다”가 아니라 “녹음 경로가 소리를 담지 못했다”입니다. 스트림이 있을 때만 추출합니다.

```bash
ffmpeg -i notification.mp4 -vn -acodec pcm_s16le notification.wav
```

추출 후에는 `ffmpeg -i notification.wav -af volumedetect -f null -`로 볼륨을 확인합니다. 이 명령은 오디오 스트림이 있을 때만 의미가 있고, 지문 알고리즘을 시험하지는 않습니다. 볼륨이 매우 낮으면 마이크 권한과 녹음 시점을 먼저 봅니다.

## 2. 소리가 발생했는가

Dejavu는 매칭된 기준 음원과 점수를 돌려줍니다. 문제는 “몇 점 이상이면 성공인가”입니다. 기기, 마이크 위치, 볼륨, 주변 소음에 따라 분포가 달라지므로 예제의 값을 그대로 쓰면 안 됩니다. 같은 환경에서 네 종류의 샘플을 모읍니다.

| 종류 | 예 | 기대 |
|---|---|---|
| 양성 | 기대한 알림음이 울린 녹음 | 높은 점수 |
| 음성 A | 다른 시스템음만 있음 | 낮은 점수 |
| 음성 B | 알림음이 울리지 않음 | 낮은 점수 |
| 혼동 | 같은 앱의 다른 알림음 | 구분됨 |

양성 최솟값과 음성 최댓값 사이에 여유가 있으면 그 사이를 임계값으로 둡니다. 두 분포가 겹치면 그 샘플들에서 오류 없이 가르는 임계값이 없다는 뜻이므로, 거짓 양성과 거짓 음성을 맞바꾸거나 UI·API 검증을 더하거나 녹음 조건과 신호를 바꿉니다. 임계값을 고른 샘플과 검증 샘플은 분리하십시오. 같은 샘플로 고르고 확인하면 일반화 성능을 주장할 수 없습니다. 원문의 “TV와 가족 대화가 있는 환경에서도 매칭됐다”는 한 환경의 관찰이며, 모든 소음 조건의 성능이 아닙니다.

## 3. 기대한 소리인가

기준 음원이 실제 알림음과 다르면 양성 점수가 낮게 나옵니다. 같은 앱의 다른 알림음이 기준과 비슷하면 음성 점수가 높게 나옵니다. 그래서 기준 음원을 알림 종류별로 분리하고, 실행 로그에 점수와 기준 음원 버전을 남깁니다. 점수만 남기면 기준이 바뀐 뒤 통과 이유를 설명할 수 없습니다.

## 4. 업무가 완료됐는가

소리가 울렸다는 사실은 알림이 화면에 올바르게 표시됐거나 주문이 처리됐다는 뜻이 아닙니다. UI 스크린샷이나 API 상태 확인을 함께 해야 합니다. 실패하면 원본 녹음, 추출 파일, 사용한 기준 음원, 점수, 시나리오 단계를 보관합니다.

## 진단 순서

| 증상 | 먼저 볼 것 | 의미 |
|---|---|---|
| 항상 매칭 없음 | `ffprobe`, 신호 유무, 기준 음원·시간 창 | 매칭 없음만으로 획득 실패를 단정하지 않음 |
| 무음 구간이 대부분 | 마이크 권한, 볼륨, 녹음 시점 | 소리 발생 여부 판단 불가 |
| 양성·음성 점수가 모두 낮음 | 기준 음원 일치 여부 | 기준 불일치 또는 변환 손실 |
| 음성 점수가 높음 | 혼동 샘플과의 차이 | 오탐 |
| 매칭은 되는데 화면에 없음 | UI 스크린샷, API | 소리와 표시는 별개 |

## 정리

명령 패턴은 합성 파일로만 확인했습니다. FFmpeg 8.1에서 오디오 없는 MP4는 `ffprobe -select_streams a:0` 출력이 비었고, 무음 WAV는 pcm_s16le에 mean/max -91.0dB, 440Hz 톤 WAV는 -21.1/-18.1dB였습니다. 이는 스트림 선택과 `volumedetect`의 좁은 확인일 뿐, 실제 단말 녹음, Dejavu 인식, 임계값 정확도, 처리 시간은 시험하지 않았습니다. 대신 순서를 정했습니다. 오디오 스트림 확인 → 볼륨 확인 → 양성·음성 대조군으로 임계값 결정 → UI·API로 업무 완료 확인. 이 순서를 지키면 “소리가 났는가”와 “검증이 실패했는가”를 구분할 수 있습니다.
