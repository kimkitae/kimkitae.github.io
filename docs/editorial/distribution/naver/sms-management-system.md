# 테스트용 SMS 인증번호, 사람을 찾지 않고 확인하는 방법

테스트 자동화에서 SMS 인증번호를 확인하려면 테스트폰을 찾아가거나, 단말을 가진 동료에게 요청해야 합니다. 이 과정을 줄이려고 Android 수신 앱과 FastAPI·Redis 서버, Slack 알림, 최근 인증번호 조회 API를 만들었습니다. 다시 읽으면서 발견한 문제가 두 가지 있습니다. 보관 시간이 원문 안에서 서로 다르게 적혀 있고, 여러 실행이 같은 번호를 쓰면 코드가 어느 실행의 것인지 알 수 없습니다.

## 구조와 보관 정책의 불일치

테스트 단말의 Android 앱이 문자를 감지해 내부 서버로 보냅니다. 서버는 FastAPI와 Redis로 구성했고, 웹 화면은 WebSocket으로 갱신되며, Slack 알림과 자동화 API가 최근 인증번호를 전달합니다.

원문 본문은 인증번호를 **10분간** 유지한다고 적었지만, 코드는 `ttl=300`을 넘깁니다.

```python
await _redis.set_key(key=phone_number, value=json.dumps(sms_data), ttl=300)
await _redis.set_key(f"sms:{phone_number}", value=str(code), ttl=300)
```

`ttl=300`은 10분이 아니라 5분에 해당하는 숫자입니다. 그래도 운영에서 실제로 5분이었는지는 단정할 수 없습니다. `set_key`는 글에 정의가 없는 래퍼이고, `ttl`이 초인지 밀리초인지도 드러나지 않습니다. 확인 가능한 사실은 본문과 호출 인자가 다르다는 것뿐입니다.

지금 만든다면 정책을 상수 하나로 명시합니다. Redis의 `EX`는 초 단위입니다.

```python
await redis.set(f"sms:{phone_number}", code, ex=600)  # 10분 정책
```

배포된 값이 궁금하면 추측하지 말고 확인합니다.

```bash
redis-cli TTL sms:01000000000    # 남은 초. -1은 만료 없음, -2는 키 없음
redis-cli PTTL sms:01000000000
```

문자를 보낸 직후와 6분 뒤의 `TTL`을 비교하면 실제 만료 정책이 드러납니다.

## 최근 값 하나만 남는다

원문은 전화번호를 키로 최근 값만 저장합니다. 리스트나 이력이 아니므로, 같은 번호로 문자가 두 번 오면 두 번째가 첫 번째를 덮어씁니다. 따라서 “오래된 문자가 쌓인다”는 문제를 이 코드에서 주장할 수 없습니다. 확인 가능한 동작은 최신 값만 남는다는 것입니다.

조회 코드에는 별도 주의점이 있습니다. `get_code`는 `sms:{phone_number}` 키를 읽고 `json.loads`를 호출하는데, 저장할 때 이 키에는 코드 문자열만 들어갑니다. Python에서 `json.loads('1234')`는 정수 1234를 반환하고 `json.loads('0123')`은 예외를 냅니다. 따라서 `"1234"`는 객체가 아닌 값이 되고, 앞자리 0이 있는 코드는 조회가 실패합니다. 이는 코드를 읽어 얻은 추론이며, 당시 운영에서 실제로 그런 문자가 왔는지는 확인할 수 없습니다.

## 병렬 실행이 같은 번호를 공유할 때

아래는 실제 사고가 아니라 구조를 설명하기 위한 **합성 타임라인**입니다.

| 시각 | 실행 A | 실행 B | Redis 최근 값 |
|---|---|---|---|
| T+0s | 인증 요청 | | 없음 |
| T+5s | | 인증 요청 | 없음 |
| T+8s | | 코드 1111 수신 | 1111 |
| T+9s | 코드 2222 수신 | | 2222 |
| T+10s | | 조회 → 2222 | 2222 |

SMS 도착 순서는 요청 순서와 다를 수 있습니다. 여기서 B는 자기 코드가 아니라 A의 코드를 읽습니다. 인증번호가 요청 단위로만 유효하면 B는 실패하고, 번호 단위로 유효하면 B가 A의 코드로 통과할 수도 있습니다. 어느 쪽이든 테스트 결과가 다른 실행에 의존합니다.

줄이는 방법은 세 가지입니다.

1. **번호 대여**: 실행 단위로 번호를 잠그고 끝나면 반납합니다.
2. **상관 정보**: 수신 시각과 기대 발신 번호는 신선도 단서입니다. 두 실행이 같은 번호로 거의 동시에 요청하면 “내 요청 이후 도착”만으로 어느 실행의 코드인지 확정할 수 없습니다.
3. **제공자 상관 식별자**: SMS 본문이나 제공자 API에 실행 ID를 넣을 수 있으면 가장 정확합니다. 다만 모든 SMS에 `run_id`가 있다고 가정하면 안 됩니다. 병렬 실행이 같은 번호를 공유하면 번호 대여로 직렬화하거나 제공자 상관 식별자를 우선하세요.

## 네 가지를 구분하자

| 항목 | 보호하는 것 | 원문 상태 |
|---|---|---|
| Redis TTL | 인증번호 노출 시간 | 본문 10분, 호출 인자 300 |
| WebSocket 세션 | 화면 연결 유지 | 최대 30분 |
| 접근 제어 | 누가 등록·조회 가능한가 | 구현 기록 없음 |
| 실행 상관 | 어느 코드가 어느 실행의 것인가 | 구현 기록 없음 |

보관 시간을 줄여도 다른 실행의 코드를 읽는 문제는 사라지지 않고, 세션을 줄여도 권한 문제는 남습니다.

## TTL이 끝나도 로그에는 남을 수 있다

원문 조회 함수는 인증번호가 든 `data_json`을 정보 로그에 남깁니다. Redis 키가 만료돼도 로그 저장소의 복사본은 별개입니다. 보관 시간을 확인할 때는 Redis뿐 아니라 애플리케이션 로그도 확인하고, 새로 남기는 로그에는 값 대신 요청 ID·성공 여부·지연 시간만 기록해야 합니다.

## 지금 공개한다면

원문은 유심폰을 서랍에 두고 앱을 설치해 번호를 공유하는 편의를 강조했습니다. 그만큼 앱을 설치할 수 있는 사람이면 번호를 공유할 수 있다는 전제가 있었습니다. 승인 단말, 발신자 제한, 내부망 접근 제어는 원문에 구현 기록이 없으며 지금 공개한다면 먼저 갖춰야 할 경계입니다.

원문의 `SmsMessage.createFromPdu((byte[]) pdu)` 단일 인자 메서드는 API 23에서 deprecated 되었고, 지금은 `createFromPdu(byte[] pdu, String format)`을 사용해야 합니다([공식 문서](https://developer.android.com/reference/android/telephony/SmsMessage)). 스토어 배포 앱은 Google Play의 SMS 권한 정책도 확인해야 합니다. 발신 번호 허용 목록과 채널 ID를 설정으로 분리하고, 문자 전문과 인증번호를 로그에 남기지 마세요.
