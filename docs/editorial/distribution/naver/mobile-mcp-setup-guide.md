# AI로 모바일 테스트하기, Mobile MCP를 써 보며 든 생각

MCP(Model Context Protocol)는 AI 도구가 외부 시스템의 도구를 호출할 수 있게 해 주는 규약입니다. 모바일에 붙이면 “이 버튼을 찾아 눌러 줘”를 자연어로 시도할 수 있습니다. 편리하지만 위험한 지점도 같습니다. 모델이 “완료했습니다”라고 말한 것과 실제로 그 동작이 일어난 것은 다릅니다.

## 탐색과 회귀는 다른 문제다

| 항목 | 탐색적 사용 | 결정적 회귀 검증 |
|---|---|---|
| 목적 | 화면과 동작을 빨리 파악 | 같은 결과가 반복되는지 확인 |
| 입력 | 자연어 지시 | 고정된 시나리오와 데이터 |
| 판정 | 사람이 화면과 로그 확인 | 자동 assertion과 실패 증거 |
| 적합한 단계 | 새 기능 탐색 | 배포 전 반복 검증 |

MCP 기반 도구는 접근성 스냅샷을 읽어 요소를 나열하고 탭·입력·스크린샷을 실행합니다. Appium처럼 세션과 셀렉터를 관리하지 않아도 되므로 시작 비용이 낮습니다. 대신 같은 지시가 같은 결과를 낸다는 보장이 없고, 모델의 판단이 assertion을 대신할 수 없습니다.

## 현재 upstream 기준으로 연결하기

Node.js, Xcode Command Line Tools, Android Platform Tools를 준비하고, [Mobile MCP 저장소](https://github.com/mobile-next/mobile-mcp)의 현재 안내를 확인합니다. 저장소 문서에는 연결 가능한 디바이스 목록과 Mobilewright 예제가 있으며, 도구 이름은 버전에 따라 달라질 수 있습니다.

Cursor는 사용자 전역 `~/.cursor/mcp.json`과 프로젝트 `.cursor/mcp.json`을 모두 사용할 수 있습니다. 어느 쪽에 등록했는지 기록하세요.

```json
{
  "mcpServers": {
    "mobile-mcp": {
      "command": "npx",
      "args": ["-y", "@mobilenext/mobile-mcp@latest"]
    }
  }
}
```

`@latest`는 시점에 따라 다른 버전을 가리키므로, 재현성이 필요하면 설치 후 실제로 해석된 버전을 기록하고 고정하세요.

## 기기와 권한의 경계

iOS 시뮬레이터는 `xcrun simctl`, Android 에뮬레이터는 AVD 이름과 API 레벨을 기록합니다. 실제 단말은 iOS의 신뢰 설정, Android의 USB 디버깅이 필요합니다. 회사 계정이 로그인된 단말을 탐색에 쓰면 계정 상태가 바뀔 수 있으므로 허용된 테스트 단말만 사용합니다.

모델은 접근성 정보에 없는 것을 “없다”고 단정하기 쉽습니다. 레이블 없는 버튼, WebView 내부 요소, 캔버스 화면은 목록에 나타나지 않을 수 있고, 좌표 탭은 해상도에 민감합니다. “요소를 찾지 못했다”는 화면에 없다는 뜻이 아니라 접근성 트리에서 찾지 못했다는 뜻입니다.

## 완료 메시지 대신 증거를 요구한다

도구 호출 결과에는 텍스트 요약, 이미지, 구조화된 결과가 모두 올 수 있습니다. “탭했습니다” 같은 모델의 문장은 실제 관찰된 도구 출력과 구분해야 하며, 그 자체가 화면 상태의 증거는 아닙니다.

1. 동작 전후 스크린샷
2. 대상 요소의 접근성 스냅샷
3. 기기 로그 또는 앱 상태
4. API·DB로 확인한 업무 상태

스크린샷만으로는 올바른 버튼을 눌렀는지, 스냅샷만으로는 화면이 실제로 바뀌었는지 알 수 없습니다. 두 증거가 같은 방향을 가리켜야 동작으로 인정할 수 있습니다.

## 탐색한 흐름을 회귀 시나리오로 바꾸기

아래는 제안하는 작업 순서의 예시이며, 특정 앱이나 실제 계정에서 검증한 기록이 아닙니다.

1. “설정에서 알림 토글을 껐다 켜 줘”라고 탐색합니다.
2. 사용한 요소 식별자, 화면 전환, 걸린 시간, 실패한 시도를 기록합니다. 같은 지시를 두 번 실행하면 스모크 확인은 되지만, 두 번의 일치가 결정성을 증명하지는 않습니다.
3. 사람이 스크린샷과 스냅샷을 보고 식별자가 다른 요소와 겹치지 않는지 확인합니다.
4. 기기 모델, OS 버전, 앱 빌드, 로케일, 초기 권한 상태와 동작, assertion을 기존 프레임워크 시나리오로 옮깁니다. 새 도구를 비교한다면 upstream README의 Mobilewright 예제도 출발점이 될 수 있습니다. 이번 개정에서 실행해 검증한 경로는 아닙니다.
5. 같은 시나리오를 두 번 실행합니다. 두 번째가 실패하면 정리 누락뿐 아니라 대기 시간, 환경, 불안정한 로케이터, 제품 결함도 확인하세요. 실패 하나가 정리 누락을 증명하지는 않습니다.

자연어 지시를 그대로 테스트로 저장하면 모델이나 UI가 바뀔 때 같은 지시가 다른 동작을 합니다. 남겨야 할 것은 “모델이 성공했다”가 아니라 “검토된 재현 가능한 단계”입니다.

## 권한과 파괴적 동작

결제, 계정 삭제, 로그아웃은 탐색 중에도 확인 절차를 둡니다. 허용할 도구와 앱 범위를 정하고 테스트 계정만 사용하며, 도구 호출 로그와 실패 스크린샷을 보관합니다. 모델이 만든 시나리오는 실행 전에 사람이 검토합니다. 보안이 중요한 흐름은 아직 MCP 탐색에 맡기지 않는 편이 안전합니다.
