# 결제 화면 반복 테스트, 소프트웨어 밖으로 나가 본 이야기

결제 수단이 여러 개인 서비스를 운영하면 배포마다 주문부터 결제 완료까지 모든 수단을 확인해야 합니다. 보안이 강한 결제 화면은 캡처가 비어 있거나 가상 키패드 배열이 매번 달라서, 일반적인 UI 자동화만으로는 반복 검증이 어렵습니다. 이 글은 그 반복을 줄이려고 하드웨어를 붙여 본 실험의 중간 기록입니다. 하드웨어는 조립했지만 소프트웨어 연결은 마무리하지 못했습니다.

## 구상한 흐름

카메라로 화면을 보고, 라즈베리파이나 아두이노가 좌표를 처리하고, 서보 두 개가 XY 플로터를 움직여 목표 지점을 누르는 구성이었습니다. Appium은 앱 상태를 준비하고 클릭 결과를 다시 확인하는 역할을 맡는 설계였습니다. 원문 예시는 좌표 서버를 `0.0.0.0`에 열고 인증을 두지 않았으므로, 지금 공개한다면 내부 주소에만 바인딩하고 호출 인증과 요청 제한을 먼저 붙여야 합니다.

## 진짜 난제는 좌표 매핑이다

서보 각도와 화면 좌표는 일대일로 대응하지 않습니다. 축이 화면과 평행하지 않을 수 있고, 카메라가 비스듬하면 원근이 생기며, 서보 각도와 실제 이동 거리도 선형이 아닙니다. 가장 단순한 모델은 세 점으로 구하는 아핀 변환입니다.

운영 관점에서 확인할 것은 계산식보다 **맞춘 점과 시험할 점을 분리했는가**입니다. 화면의 세 위치와 그때의 두 축 명령을 짝지어 모델을 구하고, 계산에 쓰지 않은 네 번째 위치로 시험합니다.

| 단계 | 확인할 것 | 잘못됐을 때의 판단 |
|---|---|---|
| 기준점 세 개 측정 | 화면의 서로 다른 영역에 놓고, 세 점을 일직선에 두지 않는다 | 한쪽에 몰리거나 일직선이면 화면 전체의 변환을 결정하기 어렵다 |
| 두 축 계산 | 화면 좌표에서 X축·Y축 명령을 각각 구한다 | 한 축만 맞춘 것으로 2차원 위치를 검증했다고 볼 수 없다 |
| 독립 위치 시험 | 계산에 쓰지 않은 네 번째 점에서 예측과 관찰의 차이를 잰다 | 차이가 허용 오차를 넘으면 모델·고정 상태·기구 유격을 다시 본다 |
| 위치 변경 후 재시험 | 단말이나 카메라를 옮겼는지 확인한다 | 예전 계수를 그대로 쓰지 말고 다시 측정한다 |

이 절차는 다시 만든다면 사용할 설계안입니다. 실제 장치에서 이 측정을 수행했다는 기록은 아닙니다. 계산과 자체 점검 코드는 아래 원문에 따로 두었습니다.

세 점은 한 직선 위에 있으면 안 됩니다. 일직선 위의 세 점은 아핀 변환을 유일하게 결정하지 못합니다. 또 아핀 변환은 평행선을 평행선으로 보내므로, 카메라나 플로터가 기울어 사다리꼴 왜곡이 생기면 원근 변환(호모그래피)이 필요합니다. 호모그래피는 최소 4개의 비공선 점이 필요하고, 서보의 각도-거리 관계가 비선형이면 축별 보정 테이블이나 보간이 낫습니다.

## 캘리브레이션 절차

1. 기기와 플로터를 고정하고 알려진 좌표의 목표점을 띄웁니다.
2. 일직선이 아닌 세 점을 측정해 계수를 구합니다.
3. 네 번째 점(가능하면 다섯 번째 점도)으로 예측해 잔차를 계산합니다. 잔차가 기계적 허용 오차보다 크면 아핀 가정을 버립니다. 이 검증점들은 모델을 시험할 뿐 실제 액추에이터 정확도를 보장하지 않습니다.
4. 기기를 옮기거나 각도를 바꾸면 다시 측정합니다.

단말마다 플로터를 두는 계획이라면 이 절차가 대수에 따라 반복되므로, 공간·관리 비용에 재캘리브레이션 시간을 포함해야 합니다.

## 고정 대기 대신 완료 피드백

원문 서버는 동작 후 `time.sleep(2)`, 아두이노는 클릭 후 `delay(500)`을 둡니다. 둘 다 “이 정도면 끝났겠지”라는 가정이고, 서보 속도나 이동 거리가 바뀌면 틀립니다.

- **앱 상태 확인**: 클릭 후 Appium으로 기대한 화면 전환을 확인합니다.
- **카메라 확인**: 목표 지점의 시각적 변화를 비교합니다.
- **센서 피드백**: 리미트 스위치나 힘 센서로 실제 접촉을 감지합니다.

각 방법은 다른 실패를 잡습니다. 앱 상태는 입력이 먹혔는지 알려 주지만 화면 갱신이 늦으면 오인할 수 있고, 카메라는 물리 동작을 보여 주지만 조명에 민감하며, 센서는 접촉만 알려 줍니다. 여러 신호를 조합하면 더 잘 확인할 수 있지만, “항상 두 가지 이상이 필요하다”는 보편 규칙은 아닙니다.

## 하드웨어와 소스 레벨 훅

| 기준 | 물리 클릭 | 소스 레벨 훅 |
|---|---|---|
| 보안 화면 | 허용된 테스트 환경이면 가능 | 훅이 없으면 불가 |
| 재현성 | 물리 변수에 영향 | 높음 |
| 앱 접근 | 불필요 | 빌드·소스 필요 |
| 입력 경로 | 실제 터치를 지남 | 입력 계층을 건너뜀 |
| 비용 | 기기별 캘리브레이션 | 코드 변경 |

목표는 허용된 테스트 환경에서 사람의 반복 동작을 재현하는 것입니다. 이 글의 코드는 어떤 결제 시스템도 제어하지 않으며, 액추에이터를 실제로 구동해 검증하지 않았습니다.

원문에는 단말 크기별 플로터를 만들어 1개 단말에 1개 플로터를 연결하고, 24/7로 BDD 시나리오를 돌리고 싶다는 목표가 남아 있습니다. 그것은 목표이며, 이 글은 완성된 운영 사례로 소개하지 않습니다. 이 하드웨어는 소프트웨어 연결이 끝나지 않은 미완성 테스트 픽스처이고, 실제 서보 정확도, 클릭 성공률, 동작 지연 시간, 물리 정확도는 검증하지 않았습니다.
