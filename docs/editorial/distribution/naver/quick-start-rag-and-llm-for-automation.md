# RAG가 “결과 5개”라고 할 때, 운영자가 먼저 물어야 할 것

RAG 기반 사내 검색을 운영하다 보면 이런 화면을 만납니다. 질문을 넣었더니 “관련 스크립트 5개를 찾았습니다”라고 표시되고, 답변도 그럴듯합니다. 그런데 실제 저장소의 문서는 2개뿐입니다.

이 글은 2024년에 만든 검색 예제를 2026년에 다시 실행하며 정리한 운영 체크입니다. 당시 운영에서 같은 장애가 있었다는 기록은 아니지만, “결과 개수”라는 로그를 어디까지 믿어야 하는지는 지금도 그대로 유효합니다.

## 결과 개수는 문서 개수가 아니다

원인은 검색 라이브러리가 부족한 자리를 채우는 방식과, 그 자리를 코드가 인덱스로 읽는 방식의 조합이었습니다. 벡터 인덱스에 청크가 2개인데 5개를 요청하면, 라이브러리는 실제 이웃 2개를 반환하고 나머지 3자리를 `-1`로 채웁니다.

```text
labels = [0, 1, -1, -1, -1]
```

원본 필터는 `if i < len(scripts)`였습니다. Python에서 `-1 < 2`는 참이므로 `-1`이 통과하고, `scripts[-1]`은 마지막 청크를 뜻합니다. 그래서 2개 문서가 5개로 늘고, 마지막 문서가 네 번 등장합니다.

이때 로그에 남는 것은 “결과 5개”입니다. 실제 문서 수, 중복 수, 어느 실행의 결과인지는 보이지 않습니다.

결과가 비지 않는다고 답이 있다는 뜻도 아닙니다. 원문은 점수 임계값을 제거했으므로, 무관한 질문에도 가장 가까운 이웃이 나올 수 있습니다. “못 찾음” 분기가 있는지와 별개로, 일부러 관련 없는 질문을 넣었을 때 답변을 보류하는지도 확인해야 합니다.

## 운영자라면 이 네 가지를 요청하십시오

기술 세부를 직접 고치지 않더라도, 검색 품질을 확인하려면 다음 증거를 요청할 수 있어야 합니다.

| 요청할 증거 | 확인하는 것 |
|---|---|
| 원본 `labels` 배열 | `-1`이 섞여 있는지. 결과 개수만으로는 보이지 않는다. |
| 경로를 중복 제거한 문서 목록 | 5개 결과가 실제로 몇 개 문서인지. |
| 점수가 `0.0000`인 항목과 그 경로 | 패딩된 자리가 마지막 문서를 반복하는 단서. 다만 실제로 낮은 점수도 네 자리에서 0.0000으로 반올림될 수 있으므로 이것만으로 단정하지 않고 원본 라벨을 함께 본다. |
| 프롬프트에 실제로 들어간 문자열 | 검색 결과가 어떤 형태로 모델에 전달됐는지. 파일 경로와 함수 시그니처가 포함됐는지 확인한다. |

점수는 순위를 뒤집는 변환일 뿐 정답 확률이 아닙니다. `0.99`를 “99% 정답”으로 읽으면 임계값 판단이 틀어집니다. 이 글에서는 점수 계산법을 길게 다루지 않고, 판단에 필요한 증거만 정리합니다.

## 이 현상이 우리 시스템에도 해당하는가

이 재현은 인덱스 벡터 수가 요청 개수보다 작은 경우를 일부러 만든 것입니다. 원문의 2024년 인덱스가 실제로 얼마나 컸는지는 알 수 없으므로, “당시 이 버그가 발생했다”고 말할 수 없습니다.

큰 인덱스를 쓰면 무조건 안전하다는 뜻도 아닙니다. IVF 인덱스는 `nprobe`가 작으면 검색 후보가 부족할 수 있고, HNSW도 `efSearch`가 작거나 필터로 후보가 줄면 같은 일이 생길 수 있습니다([FAISS FAQ](https://github.com/facebookresearch/faiss/wiki/FAQ), [Index API](https://faiss.ai/cpp_api/struct/structfaiss_1_1Index.html)). 필터 검색까지 일반화하려면 인덱스와 필터 구현을 각각 확인해야 합니다.

## 문맥이 잘려서 시그니처가 빠졌다고 단정하지 마십시오

검색된 코드에 함수 시그니처가 없으면 “문맥 자르기”를 먼저 의심하기 쉽습니다. 원문 설정은 `max_chunk_size=100`, 상위 3개 내용을 공백으로 연결한 뒤 3000자에서 자르는 구조였습니다. 다만 청크를 만드는 함수가 생략돼 있어 100의 단위와 실제 청크 길이는 알 수 없습니다. 청크가 100자라고 가정하면 세 청크와 구분자 두 개를 합쳐도 최대 302자이므로, 그 경우에는 3000자 제한이 원인이 될 수 없습니다.

더 먼저 볼 것은 청크 자체입니다. 청크가 함수보다 작거나, 파일 경로 없이 내용만 이어 붙으면 모델은 어느 파일의 어떤 함수인지 알 수 없습니다. 실제로 검색된 청크와 조합된 프롬프트를 확인하십시오. 청크를 키운 설정이라면 3000자 제한이 다시 문제가 될 수 있으므로, 그때는 실제 문자열 길이와 모델의 토큰 수를 함께 세야 합니다.

## AX 도입 판단에도 같은 구분이 필요하다

교육 현장의 요청을 예로 들면, “LLM에게 물어본다”로 모든 요청을 처리하면 안 됩니다.

| 요청 | 맞는 경로 | 이유 |
|---|---|---|
| 오늘 출석 인원은? | 권한이 확인된 현재 DB 집계 쿼리 | 최신 수치가 필요하고, 생성 모델이 숫자를 추측할 자리가 아니다. |
| 보강 수업 규정은? | 버전이 지정된 승인 정책 문서 검색 + 인용 | 답변과 적용 버전을 함께 보여 줘야 한다. |
| 휴가 신청을 승인해 줘 | 권한 있는 상태 변경 워크플로 | 승인은 감사 가능한 권한 행사이지 LLM에 판단을 맡기는 일이 아니다. |

검색 결과가 잘못 들어간 RAG도 같은 원칙으로 진단합니다. 먼저 “답이 DB에 있는가”, 다음 “검색 결과가 실제 문서와 맞는가”, 마지막 “프롬프트에 근거가 들어갔는가”를 봅니다.

## 정리

검색 로그의 결과 개수는 시작점일 뿐입니다. 원본 라벨, 중복을 제거한 경로, 0으로 반올림된 점수, 실제 프롬프트를 함께 요청하십시오. 그다음 인덱스 크기와 검색 파라미터가 이 경로를 실제로 실행할 수 있는지 확인해야 합니다.
