# Appium에서 시작한 모바일 테스트 자동화, 도구를 바꾼 이유

모바일 테스트 자동화를 운영하면서 겪은 문제는 도구가 부족해서가 아니라 실패 원인을 늦게 알게 된다는 점이었습니다. 화면의 리소스 ID가 바뀐 것을 확인하려고 전체 시나리오를 다시 돌려야 한다면, 자동화는 오히려 병목이 됩니다.

## Appium에서 배운 것

Appium은 앱 외부에서 화면을 제어하는 블랙박스 방식입니다. 요소 식별자가 없으면 그 단계에서 바로 실패하지만, 당시 팀에서는 전체 스위트를 돌려 결과를 모은 뒤에야 어느 화면이 깨졌는지 알 수 있었습니다. 여러 단말을 병렬로 돌려도 피드백이 늦으면 유지보수 비용은 줄지 않습니다.

## 네이티브 프레임워크로 옮긴 이유

Espresso와 XCUITest는 앱 소스에 접근합니다. 테스트가 참조하는 식별자가 소스에 드러나서, 당시 빌드 과정에서 누락·변경을 더 일찍 확인할 수 있었습니다. 다만 임의의 문자열 셀렉터 변경을 컴파일 단계에서 모두 잡아 주는 것은 아니며, 빌드 설정과 테스트 구성에 따라 결과가 달랐습니다. 대신 개발 프로세스와 같은 속도로 관리해야 하고, 접근 권한이 있는 사람만 작성할 수 있다는 한계가 있습니다.

## 도구보다 중요한 것

Katalon 같은 로우코드 도구는 작성자 층을 넓혀 주지만, 페이지 오브젝트를 관리하지 않으면 같은 문제가 반복됩니다. 2024년 당시에는 API로 상태를 준비하고 UI는 확인 지점에만 쓰는 방식이 더 효율적인 경우도 많았습니다. 원문은 GPT로 페이지 소스를 비교해 셀렉터를 고치고 스크립트 생성을 실험하며 생산성을 높이는 중이라고 적었습니다. 지금의 조언은 자동 복구 결과를 그대로 신뢰하기보다 실패 원인 후보를 제안하는 보조 수단으로 두고, 재현 가능한 테스트로 최종 확인하라는 쪽입니다.
