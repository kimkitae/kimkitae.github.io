# 모바일 자동화에서 도구보다 먼저 정할 것

모바일 자동화 스위트가 실패했을 때 “앱이 깨졌다”와 “단말이 준비되지 않았다”와 “이전 실행 데이터가 남았다”를 구분하지 못하면, 재시도로 넘어가고 같은 실패가 다시 쌓입니다. Appium, Espresso, XCUITest, Katalon을 다룬 기록을 지금 다시 읽으며 먼저 정할 것은 도구보다 **상태 준비와 검증 지점을 나누는 기준**이라고 봅니다. 아래 예시와 진단표는 그 기준을 설명하기 위한 이번 개정의 제안입니다.

## 검증 대상을 나누면 결정이 단순해진다

| 검증 대상 | UI | API | 이유 |
|---|---|---|---|
| 값이 화면에 실제로 보이는가 | 1차 검증 | 불가 | 렌더링·포맷·접근성은 UI에만 있음 |
| 계산·권한·상태 전이 | 느리고 불안정 | 1차 검증 권장 | 서버가 최종 판단을 가짐 |
| 사용자의 한 번의 동작 | 1차 검증 | 불가 | 탭·입력 자체가 검증 대상일 때가 있음 |
| 다음 테스트의 시작 상태 | 피함 | 권장 | UI로 만들면 실패 원인이 섞임 |

예를 들어 한 시나리오를 “상태 준비 호출 1회 + UI 확인 1회”로 나눌 수 있습니다. 이는 제안한 배분 예시이며 측정된 절감 수치가 아닙니다. 대신 API로 만든 데이터는 사용자가 도달하는 경로를 통과하지 않았으므로, 그 경로는 별도 시나리오로 남겨야 합니다. 서버가 없는 오프라인 앱이라면 API 열은 비어 있을 수 있습니다.

## 네이티브가 항상 컴파일 타임 검증은 아니다

원문에서는 Espresso와 XCUITest로 옮긴 뒤 빌드 단계에서 리소스 ID 변경을 더 일찍 확인할 수 있었다고 적었습니다. 경험은 사실이지만 플랫폼별 이유가 다릅니다.

- Android의 `R.id.checkout_button`은 빌드 시 생성되는 상수입니다. 테스트가 이를 참조하면 ID가 사라질 때 컴파일이 깨집니다.
- iOS의 XCUITest는 `app.buttons["checkoutButton"]`처럼 접근성 식별자를 런타임 문자열로 조회합니다. 앱에서 식별자를 지워도 테스트는 컴파일되고 실행 중에 실패합니다.

빌드가 무엇을 잡는지는 테스트 타깃 구성과 lint 설정에도 달려 있습니다. “네이티브라서 컴파일 타임에 잡힌다”가 아니라 “참조 방식에 따라 잡히는 시점이 다르다”가 정확합니다. 소스 접근·빌드 통합과 셀렉터 검증 시점은 별개 축입니다.

Appium에 대한 오해도 정리해야 합니다. Appium은 요소를 찾는 단계에서 실패하며, 스위트 전체가 끝나야 알려 주는 도구가 아닙니다. 원문은 피드백이 늦었다고만 적고 원인을 확정하지 않습니다. 여러 단말 결과를 모아 스위트 종료 후 리포트했다면 첫 실패 확인이 늦어질 수 있지만, 이는 가능한 파이프라인 문제이지 확인된 과거 원인이 아닙니다. 도구를 바꿔도 이 실행 방식이 남으면 지연도 남을 수 있습니다.

## 테스트를 세 부분으로 나눈 예시

아래는 구조 설명을 위한 예시이며 실제 서비스 API가 아닙니다.

1. **상태 준비**: 쿠폰을 적용하지 않은 주문을 만듭니다(상품 1개, 10,000원). 응답에서 주문 ID와 `payable_total` 10,000원을 기록합니다.
2. **기대값**: 쿠폰 10% 규칙으로 9,000원을 계산합니다. 적용 전 API 금액을 기대값으로 쓰지 않습니다.
3. **업무 UI 동작**: 장바구니를 열고 쿠폰 적용 버튼을 한 번 누릅니다.
4. **검증과 증거**: 화면 총액과 API 재조회 총액이 모두 9,000원인지 확인하고, 주문 ID·기대값·전후 스크린샷·API 응답을 남깁니다.
5. **정리**: 성공·실패와 무관하게 주문을 삭제하고, 삭제 실패도 로그에 남깁니다.

이 구조에서는 주문 생성 실패가 UI 문제로 기록되지 않고, 탭 실패는 로케이터 문제로, 값 불일치는 계산·표시 문제로 좁혀집니다. 통과한 실행에서도 주문 ID와 기대값을 남겨야 다음 실행의 데이터 오염을 비교할 수 있습니다.

## 실패를 네 종류로 나누는 순서

| 분류 | 증상 | 먼저 볼 증거 | 다음 조치 |
|---|---|---|---|
| 환경·인프라 | 여러 테스트가 같은 지점에서 실패 | `adb devices`, 드라이버·OS 버전, 세션 로그 | 앱 실패로 기록하지 않고 환경부터 고침 |
| 로케이터·렌더링 | 특정 화면에서만 요소 없음 | page source·접근성 스냅샷, 스크린샷 | 대기 조건과 식별자 확인 |
| 데이터 상태 | 요소는 있는데 값이 이전과 같음 | 요청 페이로드, 조회 API, 계정 상태 | 상태 준비 고립, 정리 단계 추가 |
| 업무 규칙 | UI는 정상인데 결과 값이 다름 | 서버 로그, 계산 근거, 스펙 | 제품 결함으로 분류하고 재현 절차 기록 |

재시도로 통과한 테스트가 어느 분류였는지 남기지 않으면 같은 원인이 계속 쌓입니다.

## 자동 셀렉터 복구의 위험

원문은 2024년에 GPT로 페이지 소스를 비교해 셀렉터를 고치는 실험을 긍정적으로 적었습니다. 지금은 자동 복구 결과를 통과로 처리하면 안 된다고 봅니다. 화면에 “확인” 버튼이 두 개인데 자동 복구가 결제 확인이 아닌 다른 버튼을 고르면, 클릭은 성공하고 최종 검증이 “예외 없음” 수준일 때 테스트는 통과합니다. 사용자는 결제하지 않았는데 말입니다.

막는 방법은 세 가지입니다. 후보가 둘 이상이면 실패시키고, 기존·신규 셀렉터와 근거를 기록해 사람이 검토하며, 요소 존재가 아니라 결제 완료 같은 업무 결과를 검증합니다. 자동 복구의 정확도나 통과율은 측정하지 않았으므로 수치로 주장하지 않습니다.

## 정리

도구를 바꾸기 전에 세 가지를 확인하세요. 상태 준비를 API로 분리할 수 있는가, 실패를 원인별로 기록하는가, UI에서 반드시 볼 지점을 한두 개로 줄였는가. 이 세 가지가 갖춰지면 어떤 도구를 쓰든 실패를 더 빨리 설명할 수 있습니다.
